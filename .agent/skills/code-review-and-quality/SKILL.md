# Code Review and Quality

## Overview
Multi-dimensional code review with quality gates. Every change gets reviewed before merge — no exceptions. Review covers five axes: correctness, readability, architecture, security, and performance.

**The Approval Standard**: Approve a change when it definitely improves overall code health, even if it isn't perfect. Don't block a change because it isn't exactly how you would have written it. If it improves the codebase and follows conventions, approve it.

## When to Use
- Before merging any PR or change
- After completing a feature implementation
- When evaluating code generated by another agent or human
- After any bug fix (review both the fix and the regression test)

## The Five-Axis Review Engine

### 1. Correctness
- Does it match the spec or task requirements?
- Are edge cases handled (null, empty, boundary values)?
- Are error paths handled (not just the happy path)?
- Does it pass all tests? Are the tests actually asserting the right invariants?
- Are there off-by-one errors, race conditions, or state inconsistencies?

### 2. Readability & Simplicity
- Are names descriptive and consistent with conventions? (No `temp`, `data`, `result` without context).
- Is control flow straightforward (avoid nested ternaries, deep callbacks)?
- **Could this be done in fewer lines?** (1000 lines where 100 suffice is a failure).
- **Are abstractions earning their complexity?** (Don't generalize until the third use case).
- Are there dead code artifacts: no-op variables, backwards-compat shims, or commented-out blocks?
- **Is a new conditional bolted onto an unrelated flow?** Push the logic into its own helper, state, or policy.

### 3. Architecture
- Does it follow existing patterns or introduce a new one? If new, is it justified?
- Does it maintain clean module boundaries and directional dependencies?
- **Does this refactor reduce complexity or just relocate it?** Count the concepts a reader must hold. Prefer restructuring that makes whole branches, modes, or layers disappear.
- **Is feature-specific logic leaking into shared modules?** Keep logic in its owning layer.
- Are type boundaries explicit? Question gratuitous `any`, `unknown`, and silent fallbacks.

### 4. Security
- Is all external input validated with strict schemas at system boundaries?
- Are database queries parameterized (zero string concatenation)?
- Are secrets kept out of code, logs, and version control?
- Are authorization checks verified per resource, not just authentication?
- Are external data flows (APIs, webhooks, LLM outputs) treated as untrusted?

### 5. Performance
- Any N+1 query patterns?
- Any unbounded loops or unconstrained data fetching?
- Any missing pagination on list endpoints?
- Any large objects created in hot paths or unneeded UI re-renders?

## Structural Remedies (Prescriptive Feedback)
When flagging a problem, propose the named restructuring move — not just the complaint:
- **Replace a chain of conditionals** with a typed model or explicit dispatcher.
- **Collapse duplicate branches** into a single clearer flow.
- **Separate orchestration from business logic** so each reads cleanly on its own.
- **Move feature-specific logic** out of a shared module into its owning package.
- **Reuse canonical helpers** instead of bespoke near-duplicates.
- **Delete pass-through wrappers** that add indirection without clarifying APIs.
- **Extract helpers or split large files** when approaching file inspection thresholds (~1000 lines).

## Change Sizing Discipline
- **~100 lines changed**: Ideal. Reviewable in one sitting.
- **~300 lines changed**: Acceptable for a single logical self-contained change.
- **>1000 lines changed**: Too large. Must be split into vertical slices or stacked PRs.
- **Total File Size Signal**: Files approaching ~1000 total lines signal an inspection point. Decompose and extract helpers before adding more logic.
